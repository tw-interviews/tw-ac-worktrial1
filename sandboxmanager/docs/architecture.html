SandboxManager Architecture

A Go JSON API that turns “run this image” into an isolated, quota-bounded, self-expiring Kubernetes pod whose workspace survives pause and delete as an S3 snapshot, plus a Python SDK that makes each sandbox feel like a local object.

  • API Go 1.25 · net/http
  • k8s client-go v0.35
  • DB Postgres 17 · pgx/v5
  • CRD agents.x-k8s.io/v1beta1
  • Cluster EKS v1.37 · 5 × c7i-flex.large
  • Files emptyDir · node agent · S3
  • SDK Python ≥ 3.9 · httpx

01Overview

SandboxManager (binary, image and Kubernetes objects: sandbox-manager) is a stateless HTTP service. It does not run its own controller. Instead it renders Sandbox objects for the upstream kubernetes-sigs agent-sandbox controller, keeps a record of each one in Postgres, and talks to the Kubernetes API for everything else: admission dry-runs and exec streams. File I/O on sandbox workspaces is done by sandbox-agent, a small DaemonSet with one agent per node, which also saves workspaces to S3 and restores them.

The service owns four concerns:

Sandboxes

Create, list, inspect and delete. Each sandbox is one user container with a TTL that every bit of activity extends.

Executions

Run argv in the user container over the exec subresource, record status, exit code and capped output.

Files

A 1Gi emptyDir per sandbox at /workspace, saved to S3 on pause, delete and just before expiry, and readable for 12h after the sandbox is gone.

Housekeeping

A GC loop removes expired snapshots and rows; snapshot loops save sandboxes about to expire and restore resumed ones.

A small notes CRUD (/notes) is still served from the same binary. It is the project's original demo endpoint and is independent of sandboxes. Several names (webapp namespace, Postgres DB/user, the webapp/sandbox-id label) intentionally keep that original name.

02System topology

The service runs on an EKS cluster (the local k3d cluster runs an older version without the agent). The control plane (API, database, node agents) lives in namespace webapp. User workloads live in namespace sandboxes, which has its own quota, limits and network policy. Workspaces are emptyDir volumes on each node's disk; the agent on that node reads and writes them, and moves them to and from an S3 bucket. Clients reach the API through kubectl port-forward; the API itself has no authentication.

04Sandbox lifecycle

Creating a sandbox

Create is designed so that a failure at any step leaves nothing behind, and so that quota problems surface as a fast, clear 429 instead of a Sandbox that never becomes ready. The DB transaction stays open across the cluster calls and commits only once the Sandbox object exists. The POST returns as soon as that commit lands; the pod starts in the background and clients poll for Ready.

Status model

The database stores the record; the status is computed on every read by combining the row with the live Sandbox object (observe in sandbox.go). Gone sandboxes keep their row, executions and latest snapshot for the recovery window (VOLUME_RETENTION, default 12h) and then the GC removes them.

TTL mechanics

  • Create sets spec.shutdownTime = now + ttl with shutdownPolicy: Delete, so the upstream controller deletes the Sandbox on expiry. No timer runs in the API. Times are rounded up to whole seconds because shutdownTime has second precision.
  • Every execution calls extendTTL(timeout): UPDATE … SET expires_at = GREATEST(expires_at, now + timeout + ttl) under the row lock, then a merge-patch of shutdownTime, then commit. Expiry never moves backwards, and concurrent executions serialize on the row lock, so the cluster always ends up with the latest value.
  • File transfers call keepAlive, which refreshes the TTL right away and every 30 s until the transfer ends, always in the background: a write holds the row's KEY SHARE lock, and a synchronous refresh could queue behind a pending pause that is itself waiting for the write.
  • Rows with ttl_seconds IS NULL predate TTLs and never expire.

Pausing and resuming

Pause uses the upstream spec.operatingMode: Suspended deletes only the pod. Because the workspace is an emptyDir, it is saved first. The pause holds the sandbox's row lock throughout, so executions and file writes wait and the snapshot includes everything written before the pause.

Deleting

DELETE takes the row lock, has the agent snapshot a running sandbox's workspace, removes the Sandbox in the cluster (NotFound is fine) and returns without waiting for the pod; terminationGracePeriodSeconds: 5 frees quota quickly even for PID-1 processes that ignore SIGTERM. A normal delete sets deleted_at and keeps the snapshot for recovery. ?purge=true deletes all of the sandbox's snapshots and its row (cascading to executions) at once, without snapshotting. If any step fails, nothing changes and the caller can retry, or purge.

Garbage collection

gc.go runs every minute in every replica, but each pass first takes pg_try_advisory_xact_lock(0x5ADB0C5), so only one replica collects at a time. A pass deletes, for rows whose deleted_at or expires_at is older than the retention: the Sandbox (if still there), every object under the sandbox's S3 prefix (a legacy sandbox's PVC instead), then the row. The bucket's lifecycle rule (10 days, and incomplete multipart uploads after one) is only a backstop.

05Inside a sandbox pod

Each pod has exactly one user container, always named sandbox (userContainerName), annotated as kubectl.kubernetes.io/default-container and labelled webapp/sandbox-id. There is no sidecar: file I/O is done from outside the pod by the agent on its node, so it works with any user image (even one without a shell or tar) and never runs inside the user's container.

06Executions

An execution is one argv run in the sandbox container. A sandbox can have any number of them, including several at once. The HTTP request stays open until the command finishes; the row is written as running first so the execution is visible while it runs, and the final update uses a context that survives client disconnects.

07Files and snapshots

Paths in the API are relative to /workspace (a leading /workspace/ is accepted). A running sandbox's files are read and written by the agent on its pod's node; a paused or gone sandbox's files come from its latest snapshot in S3, a tar of the whole workspace.

When snapshots are taken

EventWhat happens
PauseSnapshot under the row lock, before the pod is deleted. Failure → 502 and the sandbox keeps running.
DeleteSnapshot under the row lock, then delete. ?purge=true skips it and deletes all snapshots.
ExpiryA loop (every 10 s) snapshots running sandboxes expiring within 60 s that have no snapshot from that window yet. Activity pushes the expiry out, which re-arms it.
Resume, pod replacedRestore: the new pod's wait container holds it until the agent has extracted the latest snapshot.
Node or pod lost while runningNothing is saved: the sandbox comes back with its last snapshot (if it had been paused before), and anything written since is lost.

Only pods past their init containers are snapshotted, so a pod still waiting for its restore can never overwrite a good snapshot with an empty workspace. Measured: a small workspace snapshots in about 60 ms; pause takes about 6 s in all, mostly the pod's 5 s grace period.

Path safety. .. is removed by cleaning a rooted path. Every live operation goes through Go's os.Root opened on the workspace: symlinks are followed only while they stay inside it, and absolute symlinks (such as /etc/passwd made in the user container) are refused. Restores skip tar entries that would land outside the workspace. The package has unit tests for escapes through symlinks, hostile tar entries and round trips, run on macOS and Linux.

08Data model

Postgres is the source of truth for what was requested and what ran; the cluster is the source of truth for whether it is running now. Migrations are idempotent CREATE … IF NOT EXISTS / ADD COLUMN IF NOT EXISTS statements run on every start, so new nullable columns mark legacy rows.

09Python SDK

The SDK (sdk/python, package sandbox_sdk, managed with uv) wraps the API in objects that hold runtime state. It targets Python 3.9, so it keeps from __future__ import annotations and avoids 3.10+ syntax at runtime. The design rule is that sync and async code cannot drift: all request shapes, response parsing, state and validation live in I/O-free shared modules, and the sync and async classes only add the HTTP calls.

Typical use

from sandbox_sdk import Sandbox, Resources

with Sandbox("python:3.12-slim",
             command=["sleep", "infinity"],
             resources=Resources(limits={"memory": "128Mi"}),
             ttl=600,
             files={"./src/": "src/"}) as sb:      # uploaded before the command starts
    cmd = sb.exec("python /workspace/src/main.py")  # string → sh -c
    cmd.check()                                     # raise unless exit 0
    sb.download("out/", "./results/")               # directory comes back as tar, extracted safely

What create() does

  1. With files=, plans the upload first, so missing local paths or bad destinations raise before any request.
  2. POST /sandboxes (adding stage_files: true when there are files).
  3. Streams one tar built from disk on the fly (tar_chunks, 1 MiB pieces), then POST /staging/complete. If either fails, the sandbox is purged and the error re-raised.
  4. Unless wait=False, polls GET /sandboxes/{id} every 0.5 s until Ready (default timeout 120 s). Terminal statuses raise SandboxError; the deadline raises SandboxTimeoutError.

Sync and async differences

  • Listed command output. Command.stdout on a listed command fetches output lazily. Properties cannot await, so the same access on an AsyncCommand raises OutputNotLoadedError until await cmd.refresh(), or list with commands(with_output=True).
  • Clients. The sync SDK has a process-wide default client. Async has none, because a client belongs to one event loop; an AsyncSandbox without a client opens its own and closes it on delete(), aclose() or leaving async with.
  • Cancellation. Cancelling an awaiting exec() closes the request; the server still records the result, and the process may keep running.

The SDK must track the Go API: when endpoints or JSON fields change, update _api.py, both client classes, _models.py, and the in-memory fake in tests/fake_api.py.

10Isolation and limits

Network: sandbox-isolation

  • Ingress: none.
  • Egress: kube-dns on 53, and 0.0.0.0/0 minus 10/8, 172.16/12, 192.168/16, 100.64/10, 169.254/16.
  • So no other pods, the API, Postgres, the Kubernetes API, the node or metadata addresses.
  • Enforced by k3s's built-in policy controller. Not enforced on EKS yet: the VPC CNI's network-policy mode is off.

Pod hardening

  • No service-account token, no service-link env vars.
  • wait container: nobody, no capabilities, read-only rootfs.
  • Executions only target the sandbox container.

Node agent

  • Mounts the kubelet's pods directory, which also holds other pods' Secrets and tokens on the node: keep it small.
  • Every caller needs the bearer token; on EKS that is the only check (a sandbox gets 401).
  • Root with CHOWN, DAC_OVERRIDE, DAC_READ_SEARCH, FOWNER, FSETID; read-only rootfs; no Kubernetes token.

Eviction order

  • Postgres, the API and the agents have PriorityClass sandbox-control-plane (1,000,000).
  • They request well above real use (~35Mi and ~10Mi), so the kubelet evicts sandbox pods first under memory pressure.
  • kube-system and agent-sandbox-system are not covered.

What the numbers say

  • Dropping per-sandbox volumes made sandboxes start 7–10× faster on EKS. Usable p50 went from 9.9 s with EBS to 1.37 s, and is now well under k3d's 3.8 s. What remains is pod scheduling and container start, plus about 0.4 s for the first exec.
  • EBS spent its time attaching. From the pod events of 101 EBS sandboxes: about 4 s from scheduling until the volume was attached, then about 4 s to mount it and start the containers; 5 waited about 16 s for a pool volume to detach from another node. The pool could not help, since it can't know which node a sandbox will land on.
  • EFS removed the attach (2.9 s usable) but shares one filesystem across all sandboxes, with isolation only at the access point and no per-sandbox size limit, and the node mounts are made with the node's identity. That was not good enough, which led to emptyDir plus snapshots.
  • Throughput tripled, to 1.0 sandbox/s at 4 workers (from 0.33). The namespace quota (about 12 default sandboxes) is now the ceiling: 429 retries appear at 12 workers, and the p90 under load comes from waiting for quota, not from storage.
  • The cost moved to pause and delete. A pause now uploads the workspace; for small workspaces that takes about 60 ms, and grows with workspace size. Anything written after the last snapshot is lost if the pod dies.

14Known limits

  • No authentication. Anyone who can reach the Service can create sandboxes and exec into them. Access is gated by kubectl port-forward, and the NetworkPolicy keeps sandboxes from reaching the API.
  • Timeouts don't kill processes. A timed-out execution closes its stream, but the process may keep running in the container until the sandbox goes.
  • Workspaces are only as durable as the last snapshot. If a node or pod is lost while a sandbox runs, it comes back with its last snapshot (or empty); writes since then are gone. Snapshots happen on pause, delete and just before expiry, not periodically.
  • Pause and delete cost grows with workspace size, since both upload the whole workspace as one tar; reading one file from a paused or gone sandbox also scans the snapshot from the start.
  • The node agent is a sensitive component. It mounts the kubelet's pods directory, so a bug in it can expose other pods' files on the node, not just workspaces. Keep it small and hardened.
  • No NetworkPolicy on EKS yet. Sandboxes can reach other pods there, including the agent (which requires its token) and the API (which has no authentication).
  • The workspace limit is enforced by eviction. The kubelet evicts a pod whose emptyDir passes 1Gi, rather than failing writes; the node's disk is shared by all pods on it.
  • Output caps. stdout and stderr are each capped at 1 MiB per execution, flagged with *_truncated; use files for larger output.
  • Small capacity. The quota still fits only about 12 default sandboxes, sized for the old 2 CPU VM and kept for comparable benchmarks; the EKS nodes have far more room.
  • Partial priority protection. kube-system and the agent-sandbox controller are not shielded from eviction by the PriorityClass.
  • Legacy rows. Rows from before TTLs never expire; rows from before workspaces existed are purged on delete; rows with a PVC (from before snapshots) have no files API (409), and purge and GC delete their PVC.
