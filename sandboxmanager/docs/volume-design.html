Sandbox Volume Design

Why each sandbox's volume is created by the API rather than by the Sandbox's volumeClaimTemplates, and why file transfers run in a native sidecar. These are two separate decisions, often discussed as if they were one.

Two questions, not one

Comparing native sidecars with volumeClaimTemplates mixes two layers of the design:

Who creates and owns the volume?volumeClaimTemplates on the Sandbox, or a PVC the API creates itselfAPI-created PVC sbx-<id>, with no owner

Either volume option could be combined with any file-access option. The two choices do reinforce each other, as the end of this page explains.

Question 1Who creates the volume

The deciding factor is lifetime. An owned PVC is garbage-collected with its Sandbox, and the agent-sandbox controller deletes the Sandbox when the TTL runs out (shutdownPolicy: Delete).

volumeClaimTemplates

The PVC is declared in the Sandbox spec. The controller creates it and the Sandbox owns it.

Pros

  • Simpler code. One object to create. No separate PVC call and no cleanup path in createSandbox.
  • Automatic cleanup. Kubernetes garbage collection removes the PVC with the Sandbox. A crash mid-create leaves no orphan volume.
  • Fits upstream. SandboxTemplates, SandboxClaims and SandboxWarmPools expect volumes declared this way.
  • Less RBAC. The API's service account needs no PVC permissions.

Cons

  • The volume dies with the Sandbox. No recovery window, so the output of an expired sandbox is gone at once.
  • Late quota failures. A full storage quota shows up as a Sandbox stuck in NotReady, not as a 429 at create time.
  • Less control. Naming and labels follow the controller, which makes it harder for the GC, recovery pods and dbinspect check to find volumes.

API-created PVC Used

createVolume makes sbx-<id> before the Sandbox, with no ownerReference.

Pros

  • Outlives the Sandbox. Files stay downloadable for VOLUME_RETENTION (12h) through recovery pods.
  • Quota checked up front. “exceeded quota” on the PVC create becomes a clean 429 before any Sandbox exists.
  • Full lifecycle control. ?purge=true for immediate removal, GC after retention, predictable names.

Cons

  • Cleanup is the API's job. A deferred delete on failed creates, the GC loop with an advisory lock, and deleteVolume. Bugs or long outages leak volumes.
  • Retained volumes use quota. The 40-PVC / 40Gi quota now also bounds recently deleted sandboxes.
  • Diverges from upstream. Doesn't compose with warm pools or templates without extra work.
Verdict. Recoverable output after expiry is a product requirement, and only the API-created PVC provides it. The price is owning cleanup, which gc.go and dbinspect check cover.

Question 2How files get in and out

The constraints: transfers must work with any user image, must not run in user-controlled space, and with files= the uploads must be in place before the user's command starts.

Native sidecar Used

An initContainer with restartPolicy: Always, busybox, mounting the whole volume at /volume.

Pros

  • Works with any user image. Distroless or scratch images still get uploads and downloads, since all file I/O runs in busybox.
  • Isolated from the user. Transfers never run in the user's container, so user processes can't interfere, and they work even if that container has crashed or not started.
  • Gates startup. Kubernetes waits for native sidecars' startup probes, so a probe on /volume/.staged holds the user command until uploads finish.
  • Private control files. It sees the whole volume, so markers like .staged sit outside the user's /workspace subPath.
  • One code path. filesContainer is reused for recovery pods, so live and gone sandboxes are served the same way.

Cons

  • Cost on every sandbox. Requests 4Mi, limited to 16Mi. On the 768Mi limits quota that cut capacity from about 12 to about 9 default sandboxes.
  • Slower start. The user container waits for the sidecar's startup probe even without staging.
  • More privilege. Runs as root with CHOWN, DAC_OVERRIDE and FOWNER so it can replace files any user UID wrote. A read-only root filesystem and no privilege escalation limit this.
  • Security logic in shell. Path checks (inside() with readlink -f) are a shell prelude, harder to test than Go.
  • Version floor. Native sidecars need Kubernetes 1.29+ (k3s here is 1.35). Some tools assume init containers exit.

Alternatives

What each gives up compared with the native sidecar.

Exec into the user container

  • No extra container or memory.
  • Fails on images without sh or tar.
  • Runs in user-controlled space and can't gate startup.

Init container that copies, then exits

  • Uploads land before the command starts.
  • Gone afterwards, so there's nothing to serve reads, writes or downloads.

Regular sidecar container

  • Any image, stays up for live transfers.
  • Starts alongside the user container, so staging can't hold the command.
Verdict. The native sidecar is the only option that meets all three constraints. Its cost is about 16Mi of quota and a slightly slower start per sandbox.

How the two choices fit together

  • The recovery pod that serves a gone sandbox's files only exists because the PVC outlives the Sandbox. It reuses the same files container spec as the sidecar.
  • The staging marker lives on the volume, not in the pod, so a restarted pod doesn't wait for staging again.
  • Neither choice is the main cause of slow starts. Benchmarks put ready at p50 7.4 s with volumes against 1.2 s without. About 3 s is local-path provisioning each PVC and about 2 s is attaching it; the sidecar-first start is the remainder.
